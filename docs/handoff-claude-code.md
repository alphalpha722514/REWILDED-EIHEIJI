### 1.4 開発体制（2026-11-11 ユーザー決定）【main：CLAUDE.md】【記憶】

- 実装はゲームコード・UI・操作・AI・3D表現・セーブ・小修正・リファクタリング。テストは新規・回帰テスト、失敗原因・不安定さの分析、自動検証ツールの改良。
- 文書は実装仕様書・設計文書・テスト計画・技術的な変更履歴・CLAUDE.md の技術情報・引き継ぎ仕様書。
- Claude Code の担当は、要望の整理、Codex への委任、結果のレビュー、実際のブラウザーでのテスト、スクリーンショットの評価、GitHub の管理、ユーザーへの報告と未決定事項の提示。
- STEP1　Codex が現行コードを調査する。
- STEP2　Codex が技術設計案を作る。
- STEP3　Claude Code が選択肢と未決定事項を整理し、ユーザーが仕様を決める。
- STEP4　Codex が指示を現行コードと照合して実装する。**確定仕様やコードと矛盾する箇所は変えずに報告する。**
- STEP5　Codex がテストコードを作成し、自己検証する。
- STEP6　Claude Code が Codex の環境で動かないテストを実際のブラウザーで行う。
- STEP7　Codex が検証結果を受けて修正する。
- STEP8　Claude Code が最終検収し、ユーザーに報告する。
- 実装は当面、1作業につき4回まで。目的が独立した作業は別に管理できる。同じ実装の上限を避けるために JOB を分割・再作成せず、4回で足りなければ追加承認を求める。委任を増やしても不要な再実行は避ける。
  - 上の4回の記述は当時の決定。2026-11-26 に次の運用へ更新した。
- 2026-11-26 の決定。Codex の実行は、承認された開発のまとまり（マイルストーン）ごとに暫定で12回まで。実際のサービスの枠とは別の運用上の目安とし、12回を目標にせず、終われば残りを使わない。同じ原因の修正が2回続けて失敗したら止める。上限を避けるための JOB の分割や回数の数え直しは行わない。上限を超える場合は追加の承認を得る。読み取りの調査・実装・独立レビューは役割を分けて数える。
- 正式公開の前に、実装を担当した Codex とは別の Codex が独立レビューを行う（原則読み取りだけ）。既存機能の破壊・セーブ互換・ゲームの進行・iPhone の操作・性能・二重の処理と報酬・テストの不足・テストの期待そのものの誤りを重点的に確認する。
- Codex の調査が十分なら、Claude Code は同じコードを最初から読み直さず、重要な変更・危険な処理・セーブ互換・回帰リスクを重点的に確認する。品質保証と安全確認は省かず、委任できる作業を直接行った場合は理由を示す。
- 依頼は絞り、行番号・関数名・要約で回答を受ける。長いコードは会話に貼らず、完全な差分はファイルで管理する。重複調査を避け、重要箇所を詳しく確認し、Claude Code の利用量が減ったかは取得できたデータで判断する。
- 報告には Codex への委任内容、Claude Code の直接作業と委任できた場合の理由、Codex の実行回数と変更内容、取得できたトークン量、技術的な問題、ユーザーの判断が必要な事項を含める。
- SAVE_KEY とセーブ互換、既存機能、Git での差分管理、Codex の隔離と秘密の保護、現行の実行制限を守る。同じ原因で2回失敗したら停止する。main の変更と GitHub での公開にはユーザーの承認が必要。

### 1.5 各フェーズの手順【main：CLAUDE.md】

2026-11-26 に更新。以下は従来の記録。現在の体制と手順は §1.4 の更新を参照。

1. Claude が現状整理を作る。
2. ユーザーが ChatGPT と相談する。
3. ChatGPT が実装プロンプト（指示書）を作り、ユーザーが送る。

- Claude が「準備（照合・決めてほしいこと）」の文書を作る。

- 段階ごとに作業ブランチで作る → 報告 → ユーザーが承認したら main へ。
- これまでは、ユーザーの「次へ」「次に進みましょう」のあとに次の段階を始めてきた（例：2026-11-20 14:22 → P3-E の準備、20:13 → E-2）。

## 付録 B. コードの注意（この会話で実際に踏んだこと）

- **1行の関数の中に `//` のコメントを書かない。** 後ろのコードが全部コメントになる（`kamiHideTree`・`e1Start` で起きた）。`/* */` を使う。
- 置き換えの元の文字列が2か所に当たることがある。長めの、1か所だけの文字列で置き換える。
- 上志比の形は入るたびに作り、出るときに捨てる（`ctx.own`・`onDispose`）。
  - 使い回しの置き場（`cached()`）に入れた形は、出ても残る。
  - E-2 では遠くの木と切り株の形がこれで残っていた。上志比だけで使う形は ctx に持たせる。
- 物を置く場所は、置く所そのものが歩ける所か確かめる（`kamiReach`）。
  - 少しずらした所が歩けないことがある（E-2 の山の薬草）。
- 当たり判定の種類の札：`pole`・`wall`・`prop`・`post`・`tree`・`rock`・`log`。
  - `house` は視線の遮りに使う。
  - `pillar` はボスの岩のため、ほかで使わない。
- テストが「前の形」を書き写して比べていることがある（例：`tests/chapter2-save.cjs` の `kami` の空の形）。
  - セーブの形を足したら、テストも直す。
  - 決まった変化（承認された仕様）に合わせてテストを直したときは、文書にそう書く。
- **テストを流していないのに「通った」と書かない。** この会話で一度起きて、流し直して直した。
